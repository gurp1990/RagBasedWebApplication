How the RAG app works

Three pipelines share one ChromaDB database. A PDF is processed and stored once. Semantic search and question generation both read from what was stored. Each step below names the file and the function that does the work.

RAG at a glance

Retrieve · Augment · Generate

The LLM never answers from its own memory. The app first retrieves passages from the PDF stored in ChromaDB, augments the prompt with them, and only then lets the LLM generate. That is why every answer can point back to a page.

1

Document processing

Turns a PDF into small, searchable pieces with page numbers and saves them in ChromaDB.

Runs when the app starts with an empty database, when you click Ingest samples, when you upload a PDF, or with python -m app.cli ingest.

  1. 1

    Start ingestion

    A web route or the CLI passes the PDF path to the ingestion pipeline. ingest_samples() loops over every PDF in samples/.

    main.py › lifespan() main.py › upload_pdf() main.py › ingest_sample_pdfs() ingestion.py › ingest_samples() ingestion.py › ingest_pdf(pdf_path)
    In
    PDF file path
    Out
    calls process_pdf(), then save_chunks()
  2. 2

    Read each page

    pypdf.PdfReader extracts the text of every page. Each page becomes one LangChain Document that remembers its file name and page number.

    document_processor.py › process_pdf() document_processor.py › load_pdf()
    In
    samples/computer_basics.pdf
    Out
    1 Document per page · metadata {source, page}
  3. 3

    Clean the text

    Fixes text extraction problems. Bullet glyphs extracted as DEL become “•”, extra spaces are removed, and lines the PDF wrapped mid-sentence are joined back together.

    document_processor.py › clean_text()
    Rule
    a line starting in lower case or “(” is joined to the line before it
  4. 4

    Split into chunks

    LangChain’s RecursiveCharacterTextSplitter cuts the text into pieces of about 500 characters, preferring paragraph, line and sentence breaks. Neighbouring chunks overlap by 80 characters, so a fact on a boundary is not lost. Every chunk keeps its page number and gets a chunk_index.

    document_processor.py › split_into_chunks()
    Out
    sample PDF: 1 page → 5 chunks · metadata {source, page, chunk_index}
  5. 5

    Embed and store in ChromaDB

    Old chunks of the same file are deleted first, so re-ingesting never creates duplicates. Each chunk is turned into a 768-number vector by gemini-embedding-2 with task type RETRIEVAL_DOCUMENT, then saved with its text and metadata.

    vector_store.py › save_chunks() vector_store.py › delete_by_source() vector_store.py › documents_store() llm.py › GoogleGenerativeAIEmbeddings.embed_documents()
    Out
    collection documents · ids like computer_basics.pdf::chunk-3 · cosine distance
2

Semantic search

Finds passages by meaning, not exact words, and shows each one with its page number.

Runs on the Semantic Search page (/search?q=…), the API (/api/search) or python -m app.cli search.

  1. 1

    Receive the query

    The route reads the query text (and an optional document filter) and calls the search function.

    main.py › search_page(q, source) main.py › api_search() cli.py › cmd_search()
  2. 2

    Run the search

    Trims the query and fills in defaults from settings: up to 4 results and a minimum relevance of 0.59.

    semantic_search.py › search(query, top_k, source, min_score)
  3. 3

    Embed the query

    The query is embedded by the same Gemini model as the chunks, with task type RETRIEVAL_QUERY, so both are vectors in the same space.

    llm.py › GoogleGenerativeAIEmbeddings.embed_query()
  4. 4

    Find the nearest chunks

    ChromaDB compares the query vector with every chunk vector and returns the closest ones. The score is 1 − cosine distance: 1.0 means the same meaning, lower means less related.

    vector_store.py › similarity_search() langchain_chroma › similarity_search_with_relevance_scores()
  5. 5

    Drop weak matches

    Chunks scoring below 0.59 are removed. If nothing is left, the query is not about this document, and the page says so instead of showing unrelated text.

    vector_store.py › similarity_search(…, min_score)

    Measured on the sample PDF: real questions score 0.61–0.77, unrelated questions 0.48–0.57.

  6. 6

    Show the results

    Each match becomes a SearchResult (text, source, page, chunk index, score). The template shows the passage, a page badge and a score bar.

    semantic_search.py › SearchResult templates › search.html

Worked example · computer_basics.pdf

"Difference between RAM and ROM"
  #1  page 1 · chunk 1 · 0.74  "• Memory: RAM is temporary (volatile) memory … ROM is permanent …"
  #2  page 1 · chunk 3 · 0.68
  #3  page 1 · chunk 2 · 0.67
  #4  page 1 · chunk 0 · 0.66

"capital of India"
  no chunk ≥ 0.59  →  "Not found in the document."
3

Question generation

The LLM writes 5 multiple-choice questions, each from one stored passage. Each question is checked twice before it is saved.

Runs when you click Generate questions (POST /questions/generate) or with python -m app.cli generate. Takes about 1–2 minutes with gemini-3.5-flash.

  1. 1

    Load the document’s passages

    Reads every stored chunk of the chosen PDF from ChromaDB, in original order. The questions are built only from these passages.

    main.py › generate(source) question_generator.py › generate_questions(source, count=5) vector_store.py › get_chunks(source)
  2. 2

    Pick passages across the document

    Chooses 5 passages spread evenly from start to end, so the questions cover the whole document. Every chunk is added twice more as a backup list.

    question_generator.py › candidate_passages(chunks, count)
  3. 3

    LLM drafts a question

    The passage goes into QUESTION_PROMPT. The model must answer in JSON matching QuestionDraft. It first copies the sentence it uses, then writes the question, the right answer, 3 wrong answers and an explanation.

    question_generator.py › generate_one(chunk, existing) question_generator.py › _draft_question() prompts.py › QUESTION_PROMPT llm.py › get_llm().with_structured_output()
    Out
    {source_quote, question, correct_answer, wrong_answers[3], explanation}
  4. 4

    Tidy the draft

    Removes labels such as “A)” or “b.” that the model sometimes adds (the quiz page adds its own A–D) and trims spaces.

    question_generator.py › _clean()
  5. 5

    Check 1 · rules and grounding (code)

    Rejects the draft unless it has exactly 3 distinct wrong answers, doesn’t repeat an earlier question, and quotes a sentence that really is in the passage (at least 80% of the quote’s words must appear there).

    question_generator.py › _find_problem() question_generator.py › _quote_overlap()
  6. 6

    Shuffle the options

    The code puts the correct answer and the 3 wrong ones in random order. The correct answer is therefore always one of the options and isn’t always in the same position.

    question_generator.py › _shuffled_options()
  7. 7

    Check 2 · blind answer (LLM)

    The LLM sees the passage, the question and the options, but not the intended answer. It reasons, then picks a letter. The question is kept only if its pick matches the answer from the draft. This catches wrong answer keys and questions with more than one correct option.

    question_generator.py › _blind_answer_matches() prompts.py › VERIFY_PROMPT question_generator.py › BlindAnswer

    If check 1 or check 2 fails, generate_one() drafts again for that passage, up to 3 times, then moves on to the next passage in the backup list.

  8. 8

    Store in ChromaDB

    Adds the page number, the quote and the full source passage. The document’s old questions are replaced. ChromaDB metadata can’t hold lists, so the options are saved as option_1 to option_4.

    question_generator.py › _to_record() vector_store.py › save_questions() vector_store.py › _flatten_question()
    Out
    collection questions · ids like computer_basics.pdf::q-0
  9. 9

    Show the quiz

    The Questions page reads the stored questions back and rebuilds the option lists. Clicking an option marks it right or wrong and shows the explanation, the quoted sentence and the source passage.

    main.py › questions_page() vector_store.py › get_questions() vector_store.py › _unflatten_question() templates › questions.html

Database ER diagram

PK primary key (id) FK links to the PDF ┤├ one  ·  ⋲ many

ChromaDB is a vector database, not a relational one. It has no tables or joins. Each collection holds records made of an id, a text document, an embedding and flat metadata fields. The app links records by the PDF file name in source.

On disk

chroma_db_gemini/chroma.sqlite3 holds ids, text and metadata. Each collection also has its own folder with an HNSW vector index (cosine distance).

Right now

documents: 5 chunks (computer_basics.pdf). questions: 5.

Written by

save_chunks() and save_questions() in vector_store.py. Both delete a PDF’s old records first via delete_by_source().
